# AnneAccess Role and Permission Templates

AnneAccess owns coarse RBAC: which persisted principal can perform which action
on which resource key. Host applications own the business-specific record
scope, such as tenant boundaries, ownership, assignment, customer visibility,
and membership rules.

Use this guide as a starting point for host app seeds and tests. Do not treat
the role names below as engine-enforced behavior.

## Role Vocabulary

| Role key | Typical use | Scope boundary |
| --- | --- | --- |
| `owner` | Account or user that controls a tenant, shop, organization, or workspace | Host app relation or tenant scope |
| `admin` | Internal administrator for configured resources | Usually all rows inside the host app boundary |
| `manager` | Staff member that manages master data or approves operational work | Host app business unit, location, or team |
| `operator` | Staff member that creates and updates day-to-day records | Host app workflow and assignment rules |
| `staff` | Narrow operational user for front desk, fulfillment, or service actions | Host app route, service, or location scope |
| `viewer` | Read-only internal user | Same host scopes as the user can inspect |
| `customer` | External customer principal when the host app stores customers as access principals | Session-owned customer visibility |
| `member` | External membership principal, such as loyalty or subscription members | Membership relation owned by the host app |

`customer` and `member` are often not AnneAccess roles at all. Many host apps
authenticate those actors with a separate session and derive visibility from
the session subject, for example the current customer or loyalty member. Use
AnneAccess for those external actors only when they are persisted principals
that need a reusable role / permission matrix.

## Permission Matrix Shape

Keep permission resources plural and stable, matching controller or AnneAdmin
resource keys:

```ruby
role_permissions = {
  "admin" => {
    name: "Admin",
    resources: {
      "customers" => %w[manage],
      "projects" => %w[manage]
    }
  },
  "viewer" => {
    name: "Viewer",
    resources: {
      "customers" => %w[read],
      "projects" => %w[read]
    }
  }
}
```

`manage` grants the standard actions for that same resource: `read`, `create`,
`update`, and `destroy`. It does not grant custom actions. Add explicit
permissions for custom workflow operations such as `approve`, `confirm`,
`cancel`, `earn`, or `redeem`.

## Base App Examples

### Customer Management

The customer-management sample uses the conservative matrix generated by the
installer as a starting point:

| Role | Example permissions |
| --- | --- |
| `admin` | `customers.manage`, `persons.manage`, `organizations.manage`, `customer_contacts.manage`, `projects.manage` |
| `viewer` | `customers.read`, `persons.read`, `organizations.read`, `customer_contacts.read`, `projects.read` |

This is appropriate for an internal CRUD app where row-level visibility is not
part of the sample. A tenant-aware host app should keep the same coarse
permissions and load records through host-owned tenant scopes.

### Reservation Management

The reservation-management sample separates master-data CRUD from operational
reservation workflow actions:

| Role | Example permissions |
| --- | --- |
| `admin` | `customers.manage`, `reservation_resources.manage`, `reservations.manage`, `reservations.confirm`, `reservations.cancel`, `reservations.complete`, `reservations.no_show` |
| `operator` | `customers.read`, `customers.create`, `customers.update`, `reservation_resources.read`, reservation management and transition actions |
| `viewer` | `customers.read`, `reservation_resources.read`, `reservations.read` |

Workflow actions are explicit permissions because they are not covered by
`manage` when they are custom action names.

### Restaurant Loyalty

The restaurant-loyalty sample uses resource keys that reflect both admin master
data and staff service operations:

| Role | Example permissions |
| --- | --- |
| `admin` | `loyalty_programs.manage`, `loyalty_locations.manage`, `loyalty_rewards.manage`, `loyalty_members.read`, `loyalty_points.earn`, `loyalty_points.adjust`, `loyalty_redemptions.redeem` |
| `manager` | `loyalty_programs.read`, `loyalty_programs.update`, location and reward management, member read, points earn/adjust, redemption |
| `staff` | `loyalty_members.read`, `loyalty_points.earn`, `loyalty_redemptions.redeem` |
| `viewer` | `loyalty_members.read` |

Customer-facing pages in this sample do not rely on AnneAccess. They use the
customer session and host-owned loyalty member relation to decide what the
customer can see.

## Host-Owned Record Scope Patterns

Keep these rules in the host app. AnneAccess should receive the already-loaded
record, or no record for collection actions.

### Tenant or Organization Scope

```ruby
class Project < ApplicationRecord
  scope :visible_to, ->(principal) {
    where(organization_id: principal.organization_id)
  }
end
```

Use the scoped relation for both collection and member lookups:

```ruby
authorize_access! :read, :projects
@projects = Project.visible_to(current_account).order(updated_at: :desc)

@project = Project.visible_to(current_account).find(params[:id])
authorize_access! :update, :projects, record: @project
```

### Owner or Assignee Scope

```ruby
class Task < ApplicationRecord
  scope :visible_to, ->(principal) {
    where(owner_id: principal.id).or(where(assignee_id: principal.id))
  }
end
```

Keep any exception, such as manager override, explicit in the host app's query
or service layer. Do not hide that rule inside a generic engine permission.

### Membership Relation

```ruby
class Account < ApplicationRecord
  has_many :organization_memberships
  has_many :organizations, through: :organization_memberships
end
```

Use the membership relation to build host scopes:

```ruby
organization_ids = current_account.organizations.select(:id)
@projects = Project.where(organization_id: organization_ids)
```

## Testing Checklist

For every host matrix, test more than role allow/deny:

- admin or manager allowed for expected standard actions;
- viewer denied for create, update, destroy, and custom workflow actions;
- custom action requires its explicit permission;
- nil or missing principal receives the host app's forbidden response;
- same-scope record is visible and actionable;
- cross-scope record is absent from lists and member lookups;
- scoped member lookup does not reveal whether an out-of-scope record exists;
- seeds are idempotent and do not delete removed permissions implicitly.

When using AnneAdmin, test both link visibility and server-side rejection for
direct requests. Display-only hiding is not an authorization boundary.
